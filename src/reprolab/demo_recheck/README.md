# 购物车报告复查材料

这些材料是人为构造的验收场景，预期结果尚待实际运行确认。请在用户明确开放运行验收后操作。

先在桌面创建购物车项目示例，发现并选择全部 9 项测试，运行并保存来源报告。应观察到 5 两版通过、1 改善、1 新增失败、1 原有失败、1 受阻。

每个文件修改场景从同一份初始示例开始；建议分别新建示例。只修改原项目工作区，不编辑报告里的固定快照。以下补丁在该示例仓库根目录应用。若示例已被编辑，先核对补丁，勿强制覆盖。

## 场景 A：保留断言，修复业务源码

应用 `git apply --unidiff-zero recheck-scenarios/fix-money-display.patch`，只把显示修回两位小数，保留 `test_money_display` 断言。在来源报告结果页选择全部 9 项或仅需处理的 3 项，点击“用当前工作区复查”。分别发现、核对并运行。

金额显示应从新增失败变为两版通过，共享测试文件指纹相同，“同一检查转为通过”计 1。仅复查需处理项时，前次其余 6 项列为未复查。

## 场景 B：保留错误，放宽同名测试

应用 `git apply --unidiff-zero recheck-scenarios/change-money-test.patch`，只把断言改为字符串以 `12` 开头。保留金额显示错误，从来源报告复查。

金额显示的本轮实际结果可为两版通过，但必须标明“测试文件已变化，需复核”，同一检查转为通过计 0。指纹按整个文件核对，因此该文件的所有共同目标都会标为变化。

## 场景 C：改名已选测试

应用 `git apply --unidiff-zero recheck-scenarios/rename-money-test.patch`。重新发现后，原 `tests/test_cart.py::test_money_display` 显示本次未找到，原 ID 可查看和复制。不会自动换成改名后的 ID。

先连续刷新或重开会话，确认原 ID 仍在待核对范围。明确采用可用 8 项后运行，原 ID 在来源对比中列为未复查；若手动加入新 ID，则另列为仅本次选中。原报告仍应能打开。

## 场景 D：空范围和来源失败

主动清空并重开、重新发现或刷新，选择保持为空，正式运行提示须选 1–2000 项。JSON 文件 `[]` 可用于 CLI 刷新与只读核对，正式运行不接受。

移动来源报告后比较，应提示重新定位。选择原目录副本时必须核对会话 ID、运行 ID 和报告指纹；选择同会话的其他运行应拒绝。只在一次性证据副本中修改日志，比较应因证据不一致停止。

`expected.json` 是预期检查点，不是执行记录。完整界面步骤见项目的 `docs/report-recheck.md`。


严格修复场景的补充预期见 repair-expected.json：只修复业务源码预期 verified，只放宽同名测试仍采用原检查并预期 still_failing。均为编写的验收材料，本轮未运行。完整流程见 ReproLab docs/failure-repair.md。
