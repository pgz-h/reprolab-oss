# 从失败结果准备修复并验收

本文对应未发布开发版 `0.19.0a12`。流程接入项目工作台结果详情、右键菜单和 CLI。2026-11-04 已开放本地定向运行验收，实际范围见[验证与发布状态](release-readiness.md)。

## 从一条实际失败开始

1. 在“项目检查 → 历史记录”打开要处理的那一次报告，在“检查结果”选中具体测试。详情顶部显示完整测试 ID、基线／变更后的实际状态和异常摘要。搜索和筛选不会把另一份报告作为来源。
2. 点击“准备修复说明”。工具先校验来源报告身份、执行证据与共享测试指纹，再读取历史材料；不会读取当前工作区的新源码，也不会请求模型。
3. 填写问题描述、确认的期望行为和允许修改的目标。默认包含历史实际测试；可勾选相关历史差异和两版日志片段，或取消勾选以省略。日志来自整版执行，可能含其他测试，标题会明确说明。
4. 填写完整后，右侧自动生成本地预览；未手工编辑时，修改表单或材料勾选会同步更新。逐段审阅后直接复制或导出，无需再点一次生成。选中长日志／代码后可“将选中内容标为省略”。右侧仍可直接编辑，复制与导出使用同一份全文；不会自动发送。
5. 把说明交给 AI 或开发者，在原项目中修正业务源码，保持原断言表达的行为要求。若接收者认为预期本身需要修改，应先说明事实依据，由你决定。
6. 回到原失败行，点击“验收当前修复”，再点击“冻结当前修改”。必要时选择移动后的候选工作区。冻结后直接进入简洁的条件确认页，完整指纹和时间可通过“查看来源与测试差异”展开。确认、保存和关闭操作固定在底部。
7. 审阅来源、历史异常和测试差异。同一失败项的本机草稿可预填问题与期望行为；表单标明其来源，仍需核对。消息下拉列表提供从实际异常提取的片段建议，允许改选或人工编辑；无法提取时保持空白并说明原因。不要把临时路径、随机数或当次时间作为稳定条件。问题、期望行为和消息片段会即时核对。缺项、片段不属于实际异常或候选目录改变时，界面显示原因并要求补充或重新冻结。勾选确认后，点击“保存修复案例”，保存到新文件。
8. 点击“打开案例，转到验收”，核对环境，再明确点击“开始验收”。正式执行会重新运行两版，当前案例的结论来自这次执行。
9. 查看正式报告。只有故障版本次复现确认的异常类型及消息片段、候选版同一完整测试通过，且记录完整，才显示“修复验证通过”。随后回到原项目报告，用已有“用当前工作区复查”准备相关回归，再分别发现和执行。

## 编辑同步与关闭保护

直接编辑右侧全文后，再修改问题、期望行为、修改范围、当前材料或材料勾选，手工全文会保留，并提示输入与预览尚未同步。此时暂停复制／导出，避免交付旧任务或仍包含已取消选择的日志。点击“更新预览并核对”后需明确同意替换；也可撤销左侧改动，恢复与当前预览对应的输入。重新生成后仍可撤销预览编辑。

表单缺项或超过现有长度限制时不会交付旧预览，补齐后再审阅。导出在文件选择窗口返回后再次核对状态，成功提示只在实际文件写入完成后显示。

桌面入口在短暂停止编辑后（约 350 毫秒）自动保存，正常关闭前再保存一次。成功保存时直接关闭，不反复询问；保存失败会明确显示“未保存”，可以重试。保存失败时继续保留关闭保护，避免无提示丢弃尚未保存的输入。

## 本机草稿与恢复

草稿保存在应用工作目录的 `repair-notes/drafts`，使用本机 JSON 文件，不上传。只保存问题、期望、修改范围、粘贴的当前材料、材料选择、预览及同步状态；不读取运行变量值或模型凭据。手工输入和预览中的项目文本会原样保存，不能把草稿当作加密存储。文件以仅当前用户可读写的权限新建；原子替换前写入并同步，多个进程保存时检测冲突，不覆盖较新的草稿。

重新打开同一报告的同一失败项会自动恢复；也可从“检查结果 → 更多操作 → 恢复修复说明草稿”按项目、测试和保存时间选择。草稿绑定项目路径、会话／运行 ID、报告指纹、测试 ID 与测试指纹；不会自动套用到另一份报告。恢复手工全文时不重新生成，表单冲突或缺项仍阻止复制／导出。来源移走或证据不一致时只读显示，说明核对失败；重新定位原报告后从同一失败项恢复。

“放弃草稿…”经确认删除本机草稿并关闭，原报告保留。文件损坏、未知版本、超过 1 MiB 或保存失败时显示原因并保留原文件，不静默重置；可在提示的本地目录检查。草稿不是正式案例或执行结论，也不保存编辑器的撤销栈。意外退出发生在“待保存”期间时，最后约 350 毫秒的输入可能尚未落盘。

## 严格验收预填与确认

观察到的阶段和异常类型来自已校验报告；消息片段仅是启发式建议，仍须核对是否准确表达目标故障。明显包含路径、时间、长数字、UUID 或地址的片段不会自动推荐，但这不保证其他片段稳定。工具不会从失败推断期望行为，也不会把整段日志当作可靠条件。

问题与期望可来自同一失败项的草稿。重新冻结同一来源的候选时保留这些输入，但清除确认勾选。候选摘要显示冻结时间与指纹，之后编辑原项目不会改变已冻结的候选；要检查新修改，点击“重新准备候选”。正式保存固定故障条件，实际验收仍重新运行故障版与候选版。草稿保存、恢复、预填和准备均不执行测试。

## 三份源码的角色

| 材料 | 本轮的用途 |
| --- | --- |
| 原项目报告的基线快照 | 保留为背景，展示原有通过／失败状态；不作为这次严格验收的故障版 |
| 原项目报告的变更后快照 | 必须是真正记录了该测试主体失败的那份；作为新案例的故障版 |
| 准备时冻结的当前工作区 | 作为修复候选版；之后继续编辑原项目不会修改已准备／保存的案例 |

默认采用原报告保存且校验过的**完整测试文件**，按精确测试 ID 选择单项，并将同一份文件覆入两版运行副本。各版本配置和 fixture 分别保留。候选工作区里的同名测试变化、缺失或放宽都会显示；不因为候选修改了测试而默默更换检查。差异只提供有上限的预览，正式采用的测试不截断。

第一版入口固定使用原检查，不提供直接替换测试的选项。需要新检查时，必须另行准备并重新观察故障版，确认新条件；不能把旧报告观察直接套到新测试。已有“旧版试运行”向导继续用于提交基线的其他案例流程。

批量运行中的失败可能依赖测试顺序或共享状态。正式单项执行若通过，报告显示“未复现预期故障”，同时保留历史批量失败的来源、异常与阶段；不会用历史观察替代本次复现。

## 诊断、材料范围与本地保存

第一版只支持来源报告变更后版本中，setup、call、teardown 记录齐全，准备和清理通过、主体失败的单个完整 ID。fixture 失败、收集错误、缺依赖／导入错误、跳过、xfail、超时、取消及不完整记录会说明具体原因，优先查看诊断、日志及“检查项目环境”入口。修复说明仍可用于整理受阻项，但不把这些记录当作可直接确认的业务故障。

历史材料只从校验后的报告证据读取。若要补充当前工作区信息，在“当前材料”输入区另行粘贴；最终单列为“用户另行提供，未经来源运行验证”，不混入历史观察。默认使用项目相对路径，常见凭据、连接配置字段和敏感路径会被排除或替换。模型配置与凭据文件不会作为上下文候选读取；在分享前可以继续审阅和删减全文。

复用现有上下文上限：单段 24 KiB、最多选择 12 段、全文 96 KiB。历史差异本身可能只有前 20 个变更文件及每文件 200 行的预览，截断和未选择项会写在文本内；日志明确说明只保留末尾。手工编辑超过 96 KiB 时，复制／导出暂停，删减后恢复。案例执行使用完整快照及完整测试，不受分享材料截断影响。

修复准备目录保存 `preparation.json` 与 `inputs/before`、`inputs/after`、`inputs/regression.py`。正式案例 JSON 引用同目录旁的新 `.inputs` 文件夹。请一起保留，案例之后不依赖来源报告原路径。正式报告、证据 ZIP、导入与重放保留来源与确认条件。解释器和项目依赖仍需在使用机器上准备，依赖不会自动随证据打包。

结果页“更多操作”归并固定快照重跑、复制／CSV、实际测试预览、报告重新定位及“重开已保存的修复准备”。没有当前报告时，也可通过该次级菜单重开准备目录。“导出与证据”归并证据目录、ZIP、固定快照重放与复查来源定位；常用 HTML 和证据检查继续直接可见。

## 取消、失败与重试

- 准备及大文件核对在后台完成，可以取消。发布前的取消会清理本次临时准备，不留下正式案例。保存进入提交阶段后会先完成保存，再关闭，并在结果页提示实际案例路径。
- 取消文件选择时保留当前编辑或确认内容。保存失败后保留独立准备材料，可选择新文件重试；已有案例和快照不会覆盖。成功提示只在正式文件及配套输入保存后显示。
- 读取结束会再次核对来源身份；界面也核对当前报告与完整 ID。用户已经切换报告／测试时，旧任务结果不会覆盖新详情。若冻结已经保存，会提示该准备目录供重开。
- 准备前原报告被移动，可从“更多操作 → 重新定位当前报告”定位，必须匹配会话、运行 ID、报告指纹与证据。证据不一致时停止准备。准备完成后移动原报告，不影响重开、自带材料保存案例和执行。
- 重开准备目录会重新核对自带源码、权限、测试及来源结构；需要重新确认问题、行为和稳定片段。重开正式案例会恢复已保存的来源与确认条件，不自动执行。修改原项目后若需要新候选，请回到原失败行重新冻结。

## CLI：准备和正式执行分开

以下命令为操作示例。路径为示例，占位内容须替换为实际报告、完整 ID 和确认条件。

```bash
# 只读历史材料，准备本地文本；不运行、不请求模型
reprolab project repair-note /path/to/project-run \
  --test 'tests/test_cart.py::test_money_display' \
  --problem '金额显示缺少末尾零' --expected-behavior '固定两位小数' \
  --allowed-changes 'cart.py 显示逻辑，保持原断言' \
  --log after --diff cart.py --output /path/to/notes/repair.txt

# 修复原项目后，冻结故障版和候选版；只准备
reprolab project repair-prepare /path/to/project-run \
  --test 'tests/test_cart.py::test_money_display' \
  --repository /path/to/project --output /path/to/repair-preparations

# 重开、核对，返回准备记录指纹；原报告可以已经移动
reprolab project repair-show /path/to/repair-preparations/repair-ID

# 用户确认后保存正式案例；仍不执行
reprolab project repair-save /path/to/repair-preparations/repair-ID \
  --case /path/to/cases/money-repair.json \
  --problem '金额显示缺少末尾零' --expected-behavior '固定两位小数' \
  --failure-type AssertionError --message-contains '12.00' \
  --confirm-conditions --preparation-sha256 ACTUAL_SHA256

# 用户明确发起正式双版执行，写入独立报告
reprolab verify /path/to/cases/money-repair.json --output /path/to/strict-runs
```

`repair-note` 默认包含原测试，`--omit-test` 明确省略；`--log before/after`、重复的 `--diff 相对路径` 可选。`--current-material TEXTFILE` 只接受不超过 24 KiB 的普通 UTF-8 文本，另行标为当前材料。输出 JSON 的 `text` 与导出文件一致，编辑导出的文件后可由用户直接复制／发送。

`repair-prepare`、`repair-show`、`repair-save` 不探测 Python、不收集、不执行项目；正式 `verify` 继续使用现有预检与严格执行器。缺少 `--confirm-conditions`、消息为空或不属于历史实际异常时拒绝保存。桌面与 CLI 调用同一套准备、校验、保存逻辑。

## 验收场景

| 场景 | 材料与预期 |
| --- | --- |
| 仅修复购物车源码 | 应用原示例 `fix-money-display.patch`；新案例故障 SHA 等于原报告 AFTER，预期故障版复现、候选通过 |
| 只放宽同名测试 | 应用 `change-money-test.patch`；显示测试变化，采用原测试，业务仍错时预期 `still_failing` |
| 批量失败、单项通过 | 新增顺序依赖用例；正式预期 `not_reproduced`，历史观察仍为 failed |
| fixture／依赖／skip／取消／超时 | 针对性分流用例检查原因与入口；不得保存直接严格案例 |
| 长日志、删减与导出 | 单段与总量截断可见；用户省略标记保留；预览、剪贴板、文件字节对应 |
| 移动、证据不一致、取消与保存失败 | 身份核对／停止准备；原材料可恢复或重开；发布失败清理新案例并可重试 |
| 保存、重开、交付与重放 | 校验 before/after/test 哈希和权限、来源运行、观察与用户确认条件保持对应 |

具体代码在 `tests/test_project_failure.py`、`tests/test_project_failure_ui.py`；现有报告复查用例继续保留。购物车场景的机器可读预期见 `src/reprolab/demo_recheck/repair-expected.json`。场景说明与实际执行记录分别保存，当前验证范围见[验证与发布状态](release-readiness.md)。
